## 结论

现有工程适合延续开发，不需要重写 Vue、FastAPI、SQLAlchemy、Redis 或媒体存储体系。城市记忆、上传协议、媒体派生与图片工作台已有真实业务实现和自动测试，不能统称为演示页面；但“小曦智能体”尚不存在，原聊天表单提交只会清空输入。当前旅行路线页也不等于立项书中的多日规划器。

上线前的首要问题是身份与授权缺失，而不是添加更多 AI 展示。其次应建立一条可复现、有来源、有失败状态、有服务端确认的规划／记忆工作流。现有媒体队列与删除的一致性仍有边界，必须在交付材料中保留这些限制。

## 优先级与具体风险

### P0：原 API 没有身份边界

证据：`api/app/main.py:35`、`:40` 挂载路由时无身份依赖；`routers/map_overview.py:26` 接受默认用户名，`:28` 按其查用户。`city_memories.require_visited_city:34`、`check_ins.require_user:22` 等同样依赖调用方传入的 username。`require_memory` 能确保资源属于指定用户名，但指定用户名本身未经认证，因此不构成授权。

直接复现已得到无认证 HTTP 200。对私人记忆／媒体签名 URL、写入及删除存在现实越权路径。应先提供默认拒绝的身份机制，绑定用户并约束所有旧 username 参数；单机 owner token 只能标注为单机模式，不能宣传成完整多租户账号系统。

### P1：确认动作只靠界面顺序

`city_memories.py:269` 的创建、`:406` 的删除等 confirm endpoint 可直接请求；预览端点不发放绑定用户、操作、内容摘要和期限的服务端凭据。现有前端有二次确认 UI，但不能防止 Agent 或其他客户端跳过预览。新 Agent 必须使用服务端内容绑定确认；旧业务应明确其人工直调用接口边界，并按风险补强。

`city_memories.py:283` 同一请求编号的新建只比较 city_id，正文变化会静默返回旧数据。修改路径有 payload hash，可复用这一做法补齐。并发重复写仍可能触发数据库唯一冲突，不能只用单线程重复请求证明并发幂等。

### P1：地图数据的未知状态被压成数值

`integrations/amap.py:346` 接受 NaN／Infinity，`:402` 将缺失 duration 默认成 0；直接复现已确认。Provider 回复本身属于不可信输入；不能用这些数据构造“已校验”行程。应验证有限坐标和合理范围，要求有效路线时长，并在缺资料时输出 information_missing／conditional。

`amap.py:286` 有超时和可重试错误映射，但原始代码未建立缓存、额度控制或自动有限重试。新编排器需要显式调用预算、有限重试及事件记录；不应对认证／签名错误无限重试。

### P1：手工补录能覆盖全局城市事实

`check_ins.py:122` 将用户传入名称、行政区和坐标转换为 resolved city；`:60` 的 `upsert_visit` 在已有城市时于 `:80` 覆盖 City 名称、省份及坐标，不区分 manual／ip／device。单个用户的补录可能污染后续地图与路线事实，未来多人模式影响更大。已有城市字典应保持权威来源，不用未经核验的手工字段覆盖；手工声明与地图核验状态分别记录。

### P1：后台队列具有任务丢失与重复执行窗口

`media_queue.py:43` 与 `image_queue.py:41` 使用 BLPOP，读取即移除，没有 pending 集合、ACK、租约或崩溃重领。`image_jobs.py:346` 只受理 queued／failed，而 `:357` 先把状态改 running 后调用 Provider；进程在两者之间或生成途中被中断，任务会保持 running，重新投递也不能直接恢复。

`media_uploads.py:412` 对 processing 状态再次 enqueue；`media_jobs.py` 没有原子 claim，多 worker 可能同时处理同一 asset。风险由代码顺序推断，本审查未中断真实服务做故障实验。上线需 outbox／可靠队列、租约、可重入处理及恢复测试；本次最小 Agent 不应借用这一队列来掩盖自己的执行状态。

### P1：对象存储删除与数据库一致性

`city_memories.py:453`、`:457`、`:458` 删除对象后在 `:460` 提交数据库。若第二个对象删除失败，或最终 commit 失败，数据库可能仍引用已删除对象。相似逻辑存在于媒体与图片删除。应以删除状态／outbox 和可重试清理收敛，先实现逻辑不可见再处理对象，避免假定跨系统事务。此处是确定的执行顺序及相应故障推断，没有声称已复现真实 MinIO 丢失。

### P2：并发配额与大数据量性能

`media_uploads.py:133` 聚合统计后做配额判断，`:357` 检查与后续 insert 之间没有用户锁或原子预留，两个并发请求可能都通过。`map_overview.py` 和记忆列表当前全量读取，适合小规模私人原型；不能据此宣称已支持大量照片或多人高并发。需规模化数据基准后再决定分页、聚合缓存和索引。

### P2：健康检查和运行环境

`routers/health.py:7` 只返回进程存活，不验证数据库、迁移、Redis 或 MinIO。生产应区分 liveness/readiness 和可选能力状态。`infra/compose.yml` 绑定服务端口且使用开发默认口令，应只用于本机开发；公开运行前需要秘密配置、网络隔离、TLS、备份和恢复演练。

Python 依赖主要是宽范围声明，前端有 package-lock，但尚无已核验的 Python 解析锁定环境。npm 生产审计本轮为零，不代表所有开发依赖、Python 依赖和系统二进制都无风险。
